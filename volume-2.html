Part I: Multi-Limb Finite Field Arithmetic

Section 1: Algorithmic Foundations & Reduced-Bimodulus Multiplication

To compute modular multiplications over large finite fields F_p where p is approx 2^256 or p approx 2^384, standard multi-precision representations decompose elements into vector arrays of 64-bit words (limbs). Given A, B in F_p, let:

$$A = \sum_{i=0}^{n-1} a_i \beta^i, \quad B = \sum_{i=0}^{n-1} b_i \beta^i$$

where beta = 2^64, and n = ceil(log_2(p) / 64).

Montgomery Multiplication

The standard Montgomery reduction transforms the high-cost division by p into bitwise shifts and single-word additions by representing elements in the Montgomery domain A' = A * R mod p, where R = beta^n > p such that gcd(R, p) = 1. The precomputed constant p' = -p^{-1} mod beta underpins the inner loop.

Algorithm 1: Interleaved Montgomery Multiplication (CIOS Method)

Input: A, B < p, Modulus p, Precomputed p' Output: R = A * B * R^(-1) mod p

1. Clear accumulator T = [0, 0, ..., 0] (length n + 2)

2. For i from 0 to n-1:

3. c <- 0

4. For j from 0 to n-1:

5. (c, T[j]) <- T[j] + a[j] * b[i] + c

6. (T[n+1], T[n]) <- T[n] + c

7. m <- (T[0] * p') mod 2^64

8. c <- 0

9. (c, _) <- T[0] + m * p[0]

10. For j from 1 to n-1:

11. (c, T[j-1]) <- T[j] + m * p[j] + c

12. (c, T[n-1]) <- T[n] + c

13. T[n] <- T[n+1] + c

14. T[n+1] <- 0

15. If T >= p then Return T - p Else Return T[0..n-1]

Microarchitectural Performance Metrics

  • Standard Schoolbook | n^2 multiplications | 2n^2 + 2n adds | 2n limbs | ~145 cycles
  • Karatsuba (n=4) | 9 multiplications | 3n^2 + 5n adds | 3n limbs | ~128 cycles
  • Montgomery CIOS | n^2 + n multiplications | 2n^2 + 4n adds | n + 2 limbs | ~112 cycles
  • Montgomery FIPS | n^2 + n multiplications | 2n^2 + 2n adds | 2n + 1 limbs | ~118 cycles
  • Extended Redundant | n^2 multiplications | 4n^2 adds | 1.5n limbs (51-bit) | ~88 cycles

Section 2: x86-64 Assembly Optimization (MULX / ADCX / ADOX)

Modern x86-64 microarchitectural extensions allow parallel execution of carry chains using the ADCX (Unsigned Addition with Carry Flag) and ADOX (Unsigned Addition with Overflow Flag) instructions, operating simultaneously on separate execution units (Port 0 and Port 6). Combined with non-destructive flag-free multiplication (MULX), dual carry chains compute two partial product additions per clock cycle.


; Hand-optimized 256-bit Multiplication (4-limb x 4-limb) using MULX/ADCX/ADOX
; Input:  RDI = &A, RSI = &B, RDX = &C (Output)
global multiply_256_adx
multiply_256_adx:
    mov     rax, [rsi]
    mov     rdx, rax
    mulx    r8, r0, [rdi]
    mulx    r9, r1, [rdi + 8]
    add     r1, r8
    mulx    r10, r2, [rdi + 16]
    adc     r2, r9
    mulx    r11, r3, [rdi + 24]
    adc     r3, r10
    adc     r11, 0
    mov     rdx, [rsi + 8]
    xor     r8, r8
    mulx    rbx, rax, [rdi]
    adcx    r1, rax
    adox    r2, rbx
    mulx    rbx, rax, [rdi + 8]
    adcx    r2, rax
    adox    r3, rbx
    mulx    rbx, rax, [rdi + 16]
    adcx    r3, rax
    adox    r11, rbx
    mulx    r12, rax, [rdi + 24]
    adcx    r11, rax
    adox    r12, r8
    adcx    r12, r8
    mov     [rdx], r0
    mov     [rdx + 8], r1
    mov     [rdx + 16], r2
    mov     [rdx + 24], r3
    ret

Part II: Vectorized SIMD Bit-Slicing Pipelines

Section 3: Bit-Slicing Paradigm & AVX-512 Execution Layout

Bit-slicing maps N parallel field operations across N vector register lanes by reorienting the data structure: the k-th bit of N different field elements is stored packed inside a single N-bit SIMD register. For AVX-512 (N=512), a 256-bit finite field element is represented as 256 distinct 512-bit registers (zmm0 to zmm255).

Bit-Sliced Full Adder Logic Primitive

Under bit-slicing, arithmetic additions transform entirely into bitwise logical operations:

  • Sum = A XOR B XOR C_in
  • C_out = (A AND B) OR (C_in AND (A XOR B))

#include <immintrin.h>
inline void bitsliced_full_adder(__m512i a, __m512i b, __m512i cin,
                                 __m512i &sum, __m512i &cout) {
    __m512i a_xor_b = _mm512_xor_si512(a, b);
    sum = _mm512_xor_si512(a_xor_b, cin);
    __m512i term1 = _mm512_and_si512(a, b);
    __m512i term2 = _mm512_and_si512(cin, a_xor_b);
    cout = _mm512_or_si512(term1, term2);
}

Part III: Complete Elliptic Curve Addition Laws

Section 4: Short Weierstrass & Complete Addition Formulations

Standard point addition formulas suffer from exceptional points (e.g., doubling when P = Q, or yielding identity when P = -Q), leaving implementations vulnerable to side-channel analysis (SPA/DPA). Complete addition formulas eliminate exceptional cases, executing the exact same mathematical sequence for any pair of inputs (P, Q) in E(F_p).

Renes-Costello-Batina Complete Formula for Short Weierstrass Curves

For a curve E: y^2 = x^3 + ax + b, let P = (X_1, Y_1, Z_1) and Q = (X_2, Y_2, Z_2) in homogeneous projective coordinates. The complete addition algorithm proceeds through 31 field operations without branching:

$$t_0 = X_1 \cdot X_2, \quad t_1 = Y_1 \cdot Y_2, \quad t_2 = Z_1 \cdot Z_2$$ $$t_3 = X_1 + Y_1, \quad t_4 = X_2 + Y_2, \quad t_3 = t_3 \cdot t_4$$ $$t_4 = t_0 + t_1, \quad t_3 = t_3 - t_4, \quad t_4 = Y_1 + Z_1$$ $$t_5 = Y_2 + Z_2, \quad t_4 = t_4 \cdot t_5, \quad t_5 = t_1 + t_2$$ $$t_4 = t_4 - t_5, \quad t_5 = X_1 + Z_1, \quad t_6 = X_2 + Z_2$$ $$t_5 = t_5 \cdot t_6, \quad t_6 = t_0 + t_2, \quad t_5 = t_5 - t_6$$ $$X_3 = t_1 - a \cdot t_5 - 3b \cdot t_2, \quad Y_3 = t_1 + a \cdot t_5 + 3b \cdot t_2$$

Section 5: Unrolled Arithmetic Pipelines & Register Allocation

To minimize cache interaction and load/store bottlenecks, operations are pipeline-mapped to architectural registers (R_0 ... R_15).

  • Step 1: MUL R_0 = X_1 * X_2 (no dependency)
  • Step 2: MUL R_1 = Y_1 * Y_2 (no dependency)
  • Step 3: MUL R_2 = Z_1 * Z_2 (no dependency)
  • Step 4: ADD R_3 = X_1 + Y_1 (no dependency)
  • Step 5: ADD R_4 = X_2 + Y_2 (no dependency)
  • Step 6: MUL R_3 = R_3 * R_4 (read R_3, R_4)
  • Step 7: ADD R_4 = R_0 + R_1 (read R_0, R_1)
  • Step 8: SUB R_3 = R_3 - R_4 (read R_3, R_4)
  • Step 9: MUL_CONST R_5 = R_2 * (3b) (read R_2, const 3b)

Part IV: Multi-Scalar Multiplication (MSM) & Precomputation Engines

Section 6: Pippenger's Exponentiation Scheme

Multi-Scalar Multiplication (MSM) computes the linear combination of N elliptic curve points P_i and scalars k_i:

$$Q = \sum_{i=1}^{N} k_i P_i$$

Pippenger's algorithm segments b-bit scalars into c-bit windows. Let r = ceil(b / c).

For each window j in [0, r-1], bucket accumulators B_k (where k in [1, 2^c - 1]) are populated, followed by a summation reduction step:

$$S_j = \sum_{k=1}^{2^c - 1} k \cdot B_k$$

Final Result: $$Q = \sum_{j=0}^{r-1} 2^{jc} S_j$$


#include <vector>
struct Point { uint64_t x[4], y[4], z[4]; };
void accumulate_buckets(const std::vector<Point>& points,
                        const std::vector<uint16_t>& window_scalars,
                        Point* buckets, size_t num_points) {
    for (size_t i = 0; i < num_points; ++i) {
        uint16_t bucket_idx = window_scalars[i];
        if (bucket_idx > 0) {
            complete_add_inline(&buckets[bucket_idx], &points[i]);
        }
    }
}

Section 7: Hardware Lookup Engines & Memory Bandwidth Elimination

To bypass dynamic scalar multiplication latencies, precomputed lookup tables (LUTs) store pre-doubled and pre-added combinations of fixed points. Window size c = 12 gives optimal GPU/thread balance; c = 18 creates high L3 cache pressure.

Cache-Line Aligned Prefetch Engine


void prefetch_bucket_pipeline(Point* buckets, const uint16_t* scalar_windows, size_t n) {
    const size_t PREFETCH_DISTANCE = 16;
    for (size_t i = 0; i < n; ++i) {
        if (i + PREFETCH_DISTANCE < n) {
            uint16_t future_idx = scalar_windows[i + PREFETCH_DISTANCE];
            _mm_prefetch(reinterpret_cast<const char*>(&buckets[future_idx]), _MM_HINT_T0);
        }
        uint16_t current_idx = scalar_windows[i];
        if (current_idx > 0) {
            complete_add_inline(&buckets[current_idx], &points_global[i]);
        }
    }
}

Part V: Production C++/CUDA High-Performance Acceleration Routines

Section 8: Heterogeneous Host-Device Architecture

The hybrid host-GPU MSM pipeline splits the workload into streamable stages: scalar decomposition on the CPU host, async transfer to device memory, parallel bucket accumulation across CUDA thread blocks, and prefix-sum reduction on the host.

HOST (CPU): Scalar Processing -> Window Partitioning & Bucketing || Host-To-Device Async Copy DEVICE (GPU): Grid Layout (Window Slices as Blocks -> Threads as Buckets), Inter-Warp Atomic Accumulation over Shared Memory || Device-To-Host Async Copy HOST (CPU): Final Horner-Scheme Window Accumulation

Section 9: Complete High-Performance CUDA Kernel


#include <cuda_runtime.h>
#include <cstdint>
#define LIMBS 4
#define WARP_SIZE 32
struct FieldElement { uint64_t limb[LIMBS]; };
struct PointJacobian { FieldElement X; FieldElement Y; FieldElement Z; };

__device__ __forceinline__ void add_cc(uint64_t& r, uint64_t a, uint64_t b, int& carry) {
    asm volatile(
        "add.cc.u64 %0, %1, %2;\n\t"
        "addc.u64 %3, 0, 0;\n\t"
        : "=l"(r), "+r"(carry) : "l"(a), "l"(b));
}
__device__ void field_add_device(const FieldElement* a, const FieldElement* b, FieldElement* c) {
    asm volatile (
        "add.cc.u64 %0, %4, %8;\n\t"
        "addc.cc.u64 %1, %5, %9;\n\t"
        "addc.cc.u64 %2, %6, %10;\n\t"
        "addc.u64    %3, %7, %11;\n\t"
        : "=l"(c->limb[0]), "=l"(c->limb[1]), "=l"(c->limb[2]), "=l"(c->limb[3])
        : "l"(a->limb[0]), "l"(a->limb[1]), "l"(a->limb[2]), "l"(a->limb[3]),
          "l"(b->limb[0]), "l"(b->limb[1]), "l"(b->limb[2]), "l"(b->limb[3]));
}
__global__ void msm_accumulate_kernel(
    const PointJacobian* __restrict__ d_points,
    const uint32_t* __restrict__ d_scalars,
    PointJacobian* __restrict__ d_buckets,
    size_t num_points, uint32_t window_bits, uint32_t window_shift) {
    uint32_t tid = blockIdx.x * blockDim.x + threadIdx.x;
    if (tid >= num_points) return;
    uint32_t scalar = d_scalars[tid];
    uint32_t bucket_idx = (scalar >> window_shift) & ((1U << window_bits) - 1);
    if (bucket_idx > 0) {
        PointJacobian* target_bucket = &d_buckets[blockIdx.x * (1U << window_bits) + bucket_idx];
        point_add_complete(target_bucket, &d_points[tid], target_bucket);
    }
}

Section M: Worked Example - Montgomery Reduction by Hand

Take the toy parameters $R = 256 = 2^8$ and the prime $p = 13$ (with $\gcd(R, p) = 1$). The Montgomery constant is $p' = -p^{-1} \bmod R$. Since $13 \cdot 197 = 2561 \equiv 1 \pmod{256}$, we get $p' = -197 \equiv 59 \pmod{256}$.

Reduce $T = 200$ (which satisfies $T < R\cdot p = 3328$):

  • $m = (T \bmod R)\cdot p' \bmod R = 200 \cdot 59 \bmod 256 = 11800 \bmod 256 = 24$
  • $t = (T + m\cdot p)/R = (200 + 312)/256 = 2$
  • $t = 2 < p$, so no final subtraction is needed; the result is $2$.

Check: $T\cdot R^{-1} \bmod p = 200 \cdot 256^{-1} \bmod 13$. Since $256 \equiv 9$ and $9^{-1} \equiv 3 \pmod{13}$, this equals $200 \cdot 3 = 600 \equiv 2 \pmod{13}$. The reduction is exact, and the only "division" performed was the shift by $R = 2^8$.
